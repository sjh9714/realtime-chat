# N+1 해결 전후 — 같은 조건에서 나란히 (2026-08-08)

그동안 "이전 구현을 지금 커밋에서 재현할 수 없어 개선율을 싣지 않는다"고 적어 왔다.
**틀린 판단이었다.** 수정 직전 커밋은 지금도 그대로 돌아간다 — Spring Boot 버전이 같고,
스키마를 `schema.sql`로 자족적으로 만들고, 지금 k6 스크립트가 부르는 엔드포인트를 전부 갖고 있다.

## 무엇과 무엇을 비교했나

| | 커밋 | 날짜 |
| --- | --- | --- |
| before | `787781c` | 2026-02-08 — N+1 해결·인덱스·캐시가 들어오기 **직전** |
| after | `71fe9a0` | 2026-08-08 — 현재 |

> ⚠️ **이 차이는 N+1 수정 하나의 몫이 아니다.** 두 커밋 사이에는 JPQL 프로젝션·IN 배치뿐 아니라
> 인덱스 5개와 Redis Cache Aside가 함께 들어갔다(`4c37aa3` 및 이후). 여기서 재는 것은
> **그 최적화 작업 전체의 전후**다.

## 어떻게 쟀나

- **부하 도구는 같은 파일** — 현재 커밋의 `k6/rest-api-test.js`를 before에도 그대로 썼다.
  이 스크립트는 도입 이후 한 번도 바뀌지 않았다(`git log`로 확인).
- 반복마다 채팅방 목록 → 방 상세 → 메시지 이력 3회 호출. setup에서 유저 200명·방 10개·참여 1,990건.
- **매 실행 전 DB·Redis·Kafka를 볼륨까지 지우고 새로 만든다.** 같은 fixture에서 시작한다.
- 앱은 호스트에서 `java -jar`로 띄우고, `Started RealtimeChatApplication` 로그를 본 뒤 5초 더 기다렸다.
- Apple M4 · macOS 26.3.1 · Docker Desktop 29.4.3 · k6 v1.5.0.
- before는 `apache/kafka:3.9.0` 이미지가 그 사이 갱신되며 `KAFKA_LISTENERS`의 `0.0.0.0` 표기를
  거부해, 지금 compose가 쓰는 `:포트` 표기로만 바꿨다. **애플리케이션은 손대지 않았다.**

## 결과 1 — 10 VU (포화되지 않는 구간)

여기가 쿼리 수 차이가 그대로 드러나는 구간이다.

| | before `787781c` | after `71fe9a0` |
| --- | ---: | ---: |
| median | 9.94ms · 9.12ms | **1.82ms · 1.83ms** |
| p95 | 105.99ms · 97.35ms | **75.86ms · 76.37ms** |
| avg | 32.22ms · 29.79ms | **22.23ms · 22.27ms** |
| 반복/초 | 40.8 · 45.7 | **64.9 · 64.6** |

**median 9.5ms → 1.8ms.** 방 개수만큼 늘던 쿼리가 3회로 고정되면서 대부분의 요청이
한 자릿수 밀리초 안에 끝난다.

## 결과 2 — 200 VU (양쪽 다 포화)

| | before | after |
| --- | ---: | ---: |
| RPS | 173.0 · 195.5 | **244.0 · 254.7** |
| p95 | 620.95ms · 619.73ms | 691.75ms · 654.1ms |
| 요청 수 | 17,077 · 17,251 | **21,700 · 22,450** |
| HTTP 실패 | 0 | 0 |

**처리량은 30~40% 늘었지만 p95는 나아지지 않았다.** 200 VU에서는 둘 다 포화 상태라
지연이 대기 시간에 묻힌다. 병목을 없앤 만큼 더 많이 받아들이고, 그만큼 큐가 길어진다.
**이 구간의 p95를 개선 지표로 쓰지 않는다.**

## 주장하지 않는 것

- 위 절대 수치는 `docs/evidence/REST_ROOMLIST_REPEAT3_2026-08-06.md`의 값과 **비교할 수 없다.**
  그 실행은 앱을 Docker 컨테이너로 띄웠고(`app-1`, 8081), 이 실행은 호스트에서 `java -jar`로
  띄웠다. 기계 상태도 다르다. **전후 비교는 오늘 나란히 잰 이 문서 안에서만 유효하다.**
- 두 커밋 사이의 모든 변경이 포함된 값이다. N+1 수정 단독의 몫이 아니다.
- 로컬 단일 머신 측정이다. 운영 성능 주장이 아니다.
- before 첫 실행 1회는 앱이 완전히 뜨기 전에 부하가 시작돼 버렸다(요청 2,184건).
  기동 로그를 기다리도록 고친 뒤의 실행만 싣는다.
