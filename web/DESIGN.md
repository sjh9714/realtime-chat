# DESIGN.md — 실시간 채팅 데모

이 파일이 화면의 기준이다. 새 화면을 만들 때 여기 없는 값을 즉석에서 정하지 않는다.

## 어디서 왔나

**Linear** (linear.app, 2026-08-07 실측)

| | 값 |
|---|---|
| 배경 | `rgb(8, 9, 10)` — 순검정이 아니라 아주 살짝 푸른 |
| 글자 | `#f7f8f8` (3,004회) |
| 회색 계단 | `#62666d` 383 · `#d0d6e0` 205 · `#e2e4e7` 142 · `#8a8f98` 138 |
| 면 구분 | `rgba(255,255,255,0.05)` 84회 — 선이 아니라 아주 옅은 면 |
| 제목 | 64px / **weight 510** / 자간 −1.408px / 행간 1.0 |
| 부제 | 48px / 510 / 색은 `#8a8f98` |
| 모서리 | **2px** 48회 · 6px 43회 · 4px 28회 |
| 액센트 | 핑크 `#f79ce0`, 45회로 **아주 적게** |

**Superhuman** — *"premium dark UI, keyboard-first, purple glow"*.
모든 동작에 단축키가 있고 명령 팔레트가 한 키 거리에 있다.

## 왜 이 방향인가

채팅은 **오래 켜 두는 화면**이다. 몇 초 보고 닫는 화면이 아니라 하루 종일 옆에 둔다.
그래서 밝고 강한 색이 아니라 어둡고 조용해야 하고, 정보가 조밀하되 눈이 아프지 않아야 한다.
Linear가 그걸 푼 방식이 **굵기 대신 회색 계단으로 위계를 만드는 것**이다 —
weight는 510에서 크게 벗어나지 않고, 대신 글자색이 네 단계로 갈린다.

그리고 채팅은 키보드로 하는 일이다. 방 전환·검색·전송이 전부 손가락이 홈 포지션에 있을 때
일어난다. 그래서 **명령 팔레트와 단축키가 장식이 아니라 기능**이다.

포트폴리오의 다른 프로젝트와 겹치지 않는다.
좌석 예약은 흑백 포스터(각진 면, 형광 하나), FinMate는 밝은 민트 클레이 모바일이다.
여기는 **조밀한 다크 프로툴**이다.

## 토큰

```css
--bg:        #08090a;   /* 가장 아래 */
--surface:   #0e1011;   /* 목록·사이드바 */
--raised:    #16181a;   /* 입력창·떠 있는 것 */
--line:      rgba(255,255,255,0.07);   /* 선이 아니라 아주 옅은 면 */
--line-firm: rgba(255,255,255,0.13);   /* 포커스된 경계 */

--text:      #f7f8f8;   /* 본문 */
--text-2:    #d0d6e0;   /* 보조 */
--text-3:    #8a8f98;   /* 메타 — 시각·상태 */
--text-4:    #80848c;   /* 가장 흐린 것. 여기서 더 흐려지면 안 읽힌다 */

--accent:    #7c8cff;   /* 하나. 내 메시지와 포커스에만 */
--ok:        #4ade80;   /* 저장됨 */
--warn:      #fbbf24;   /* 보내는 중 */
--danger:    #f87171;   /* 실패 */
```

**위계는 굵기가 아니라 색이 만든다.** weight는 450~550 사이에 둔다.
굵기로 강조하기 시작하면 조밀한 화면이 얼룩덜룩해진다.

대비: `--text-4`(#80848c)는 `--bg` 위 **5.31:1** · `--surface` 위 5.08:1 · 네이비 패널 위 4.80:1.
**이보다 흐린 색을 만들지 않는다.**

처음엔 Linear에서 본 `#62666d`를 그대로 적어 두고 "4.6:1"이라고 썼다. **틀린 숫자였다** —
실제로는 3.45:1이다. 눈으로 충분해 보였을 뿐 계산하지 않았다.
색을 정할 때는 재고 적는다.

## 타이포

| 이름 | 크기 | 굵기 | 자간 | 쓰는 곳 |
|---|---|---|---|---|
| `.title` | 20px | 550 | -0.02em | 화면 제목 |
| `.body` | 14px | 450 | -0.01em | 메시지 본문 |
| `.meta` | 12px | 450 | 0 | 시각·상태·닉네임 |
| `.kbd` | 11px | 500 | 0 | 단축키 표시 |

본문이 14px인 이유: 채팅은 한 화면에 많이 담아야 한다. 16px이면 대화가 짧아 보인다.

## 레이아웃

- 사이드바 280px 고정, 본문 가변
- 세로 리듬 4px 배수 (조밀한 화면이라 8px는 성기다)
- 모서리 **6px**. 아바타만 원형
- 그림자를 쓰지 않는다. 떠 있는 것은 배경색 한 단계와 옅은 테두리로 표현한다

## 전달 상태

이 앱의 주장이 여기 있다 — "화면에 보였다"와 "실제 저장됐다"는 다르다.

| 상태 | 표시 |
|---|---|
| 보내는 중 | `--warn` 점 + "보내는 중" |
| 저장됨 | `--ok` 점 + "저장됨" |
| 실패 | `--danger` 점 + "실패" + 다시 보내기 |

**색만으로 말하지 않는다.** 점과 글자를 함께 둔다. 색각 이상이 있어도, 점이 작아 안 보여도
글자가 남는다.

## 키보드

| 키 | 동작 |
|---|---|
| `⌘K` / `Ctrl+K` | 명령 팔레트 |
| `↑` `↓` | 팔레트 안 이동 |
| `Enter` | 전송 · 팔레트 선택 |
| `Esc` | 팔레트 닫기 |

팔레트는 방 이동과 새 대화를 덮는다. 마우스로도 전부 되어야 한다 —
단축키는 빠른 길이지 유일한 길이 아니다.

## 모션

- 기본 140ms `cubic-bezier(0.2, 0, 0, 1)`. 오래 켜 두는 화면이라 짧아야 한다
- 메시지 도착은 애니메이션하지 않는다. 계속 움직이면 읽을 수 없다
- `prefers-reduced-motion: reduce`에서 전부 0

## 접근성

- 대비 4.5:1 이상. 가장 흐린 `--text-4`가 5.31:1 (가장 밝은 면 위에서도 4.80:1)
- 상태를 색만으로 말하지 않는다
- `web/e2e/chat-flow.spec.ts`가 axe로 검사한다.
  **이 파일을 깨지 않는 것이 재작성의 성공 기준이다**
- 팔레트는 `role="dialog"` + 포커스 트랩 + `Esc` 닫기

## 교차 노드 e2e — 원인을 찾았고 통과한다

한동안 `e2e/chat-flow.spec.ts:210`("app-1 delivers to app-2 exactly once across
recovery boundaries")이 로컬에서 통과하지 않았다. **앱 결함이 아니라 실행 환경 문제였고,
그중 하나는 compose의 실제 결함이었다.**

처음에 나는 "주입된 장애에서 회복해 화면이 따라잡는 시간이 모자란 것 같다"고 적었다.
**틀린 추정이었다.** 장애 주입은 그 단언보다 뒤에서 켜지고, 단언 시간은 이미 15초였다.
로그에서 본 장애 문구가 앞선 실행에서 남은 것인데 그걸 원인으로 삼았다.

실제로 찾은 것은 셋이다.

1. **오버레이 없이 돌리고 있었다.** 데모 게이트웨이는 `/ws/app-1`을 일부러 404로 막는다
   (노드 정체를 숨기는 게 공개 데모의 요건이고, 그걸 검증하는 테스트가 따로 있다).
   노드를 지정해 붙는 e2e는 `docker-compose.e2e.yml`을 겹쳐야 열린다. CI는 그렇게 한다.

2. **nginx가 업스트림 IP를 시작 시 한 번만 해석한다.** 앱 컨테이너만 다시 만들고
   게이트웨이를 두면, `/ws/app-1`이 조용히 app-2로 간다. 실제로 Alice가 app-1에 붙었는데
   `x-app-instance`가 app-2로 왔다. 게이트웨이를 함께 재시작해야 한다.

3. **Kafka 로그와 Postgres의 수명이 달랐다.** Postgres는 명명 볼륨이라 살아남는데
   Kafka에는 볼륨이 없어 컨테이너를 다시 만들 때마다 오프셋이 0부터 시작했다.
   그러면 새 메시지의 `(partition, offset)`이 예전 행과 겹치고
   `uk_messages_kafka`에 걸려 저장이 영영 재시도에 빠진다 — 저장되지 않으니 전달도 없다.
   멱등성 장치는 제 일을 하고 있었다. 두 저장소의 수명이 어긋난 게 문제였다.
   `docker-compose.demo.yml`에 Kafka 볼륨을 추가해 맞췄다.

깨끗한 스택에서 5회 연속, 전체 스위트 2회 연속 통과한다.

### 여기서 배운 것

로그에 보이는 오류가 지금 이 실패의 원인이라는 보장이 없다. 스택이 오래 떠 있으면
로그에는 여러 실행의 흔적이 섞인다. 시간을 맞춰 보지 않고 눈에 띄는 문구를 집었더니
엉뚱한 원인을 문서에까지 적었다.

그리고 "원본에서도 실패하니 내 변경 탓이 아니다"는 확인은 절반만 맞았다.
양쪽 다 **같은 잘못된 방법으로** 돌렸기 때문에 둘 다 실패한 것이었다.
비교는 방법이 옳을 때만 뜻이 있다.

## 이 재작성이 실제로 깨뜨린 것 — 대비 회귀

`.conversation-header`에 예전 밝은 테마의 `rgba(255,255,255,0.92)`가 남아 있었다.
어두운 배경 위에 흰색 92%를 얹으면 `#ebebeb`이 되고, 그 위에 내가 새로 넣은 밝은 글자
`#f7f8f8`이 놓여 **1.12:1**이 됐다.

내 대비 점검이 이걸 놓친 이유: **스타일시트를 읽어서 확인했기 때문이다.**
색은 겹쳐서 만들어지는데 파일에는 겹치기 전 값만 있다. 브라우저에 계산된 값을 물어보니
한 번에 나왔다. 앞서 `rgba(245,247,251,0.96)`을 놓친 것도 같은 이유였고,
같은 실수를 두 번 했다.

남아 있던 밝은 값 세 개를 전부 토큰으로 바꿔 앱 전체가 한 계단 위에 서게 했다.
