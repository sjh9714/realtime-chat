# DESIGN.md: 실시간 채팅 데모

이 파일이 화면의 기준이다. 새 화면을 만들 때 여기 없는 값을 즉석에서 정하지 않는다.

## 기준을 옮겼다 (2026-08-07)

처음에는 **Linear**(linear.app)를 실측해 기준으로 삼았다. 색과 회색 계단은 그 덕을 봤지만,
**Linear는 메신저가 아니다.** 프로젝트 관리 도구다.

그래서 메신저라면 당연히 있는 것들이 통째로 빠져 있었다. 연속 메시지 묶기, 날짜 구분선,
말풍선 옆 시각. 메시지 하나하나가 이름 한 줄·말풍선·시각 한 줄을 따로 써서
**1280×800 화면에 다섯 개**가 들어갔다.

concert가 DICE.fm(지정석을 팔지 않는 서비스)을 기준 삼았던 것과 같은 종류의 실수였다.

### 남은 것과 옮긴 것

| | 어디서 왔나 |
|---|---|
| 색·회색 계단·모서리·조밀함 | **Linear 실측** (아래 표). 이건 그대로 쓴다. 오래 켜 두는 화면의 값이다 |
| 밀도·묶기·날짜 구분선·시각 배치·아바타 | **Discord 실측** (2026-08-07) |
| 말풍선 패딩·모서리·최대폭 | **실측 아님.** 통용값과 카카오톡·카카오워크 참고 화면 |

**Linear 실측** (2026-08-07)

| | 값 |
|---|---|
| 배경 | `rgb(8, 9, 10)`: 순검정이 아니라 아주 살짝 푸른 |
| 글자 | `#f7f8f8` (3,004회) |
| 회색 계단 | `#62666d` 383 · `#d0d6e0` 205 · `#e2e4e7` 142 · `#8a8f98` 138 |
| 면 구분 | `rgba(255,255,255,0.05)` 84회: 선이 아니라 아주 옅은 면 |
| 모서리 | **2px** 48회 · 6px 43회 · 4px 28회 |
| 액센트 | 핑크 `#f79ce0`, 45회로 **아주 적게** |

**Discord 실측** (2026-08-07, 1440×862 · 공개 커뮤니티 채널)

| | 값 |
|---|---|
| 본문 | 16px / 행간 22px / weight 400 |
| 아바타 | 40px 원형 |
| 이름과 시각 | **한 줄에 나란히.** 시각은 작고 흐리게 |
| 묶음 첫 줄 높이 | 중앙값 70px · 앞 메시지와 간격 17px |
| 한 화면 메시지 | **8개** |
| 날짜 구분선 | 있음 (`2026년 7월 27일`) |

> Discord에서는 기하값만 읽었다. 대화 내용은 읽지도 기록하지도 않았다.

**Discord·Slack은 말풍선이 없는 평면 행 계열이다.** 그대로 베끼면 또 엉뚱한 것을 기준
삼는 셈이라, 옮겨지는 것(밀도·묶기·구분선)만 가져오고 말풍선 자체는 카카오톡 계열로 둔다.
업무 대화라도 한국 메신저(카카오워크·잔디)는 말풍선을 쓴다.

## 메시지 목록의 관례

| 값 | 근거 |
|---|---|
| 연속 메시지 묶기 **5분** | **실측 아님.** 통용값. 같은 사람이 5분 안에 이어 보내면 이름·아바타를 반복하지 않는다 |
| 이어지는 줄 간격 **2px** · 묶음 사이 **14px** | 사람이 바뀔 때만 크게 띄운다 |
| 시각은 **묶음의 마지막 줄에만**, 말풍선 옆에 | 전에는 메시지마다 아래 한 줄을 통째로 썼다 |
| 날짜 구분선 | 오늘·어제·`8월 5일 (수)`. 데모 시드가 5일치를 만드는데 전에는 어디가 어제인지 몰랐다 |
| 한 화면 **8개** | Discord와 같다. 전에는 5개였다 |

### 데이터가 화면을 만든다. 또

묶기를 구현했는데 데모에서 **한 번도 발동하지 않았다.** 시드가 말하는 사람을 참여자 순서대로
돌아가며 정해서 같은 사람이 두 번 이어 말하는 일이 없었기 때문이다.

대본을 `Line(speaker, text)`로 바꿔 사람을 명시하고, 이어 말하는 줄은 **1분 뒤**에 둔다
(7분씩 벌리면 5분 창을 넘겨 묶이지 않는다). concert에서 좌석 50석으로는 좌석표가
좌석표로 보이지 않았던 것과 같은 문제다.

## 전달 상태의 낱말

```
보내는 중 · 큐 접수 · 저장됨 · 실패   →   보내는 중 · 전송됨 · 전달 완료 · 실패
```

**구분 자체가 이 제품의 알맹이다.** 받아들여진 것과 실제로 남은 것은 다르다. 그건 그대로 둔다.
바꾼 것은 낱말이다. 쓰는 사람은 큐가 무엇인지 알 이유가 없다.

## 혼자 보는 화면이 아니게 한다

**전에는 메시지를 주고받을 수가 없었다.** 둘러보기가 언제나 `alice@demo.local`로 로그인해서
창을 두 개 열어도 둘 다 같은 사람이었다. 보내도 아무도 답하지 않고, 3인 방에 "1명 온라인"이 떴다.

실시간 전달이 이 제품의 전부인데 **방문자는 그걸 한 번도 보지 못했다.** e2e는 교차 노드
정확히 한 번 전달까지 증명하지만 사이트는 아무것도 보여주지 않았다.
"실제 서비스가 아니라 보여주기 식"으로 읽힌 뿌리가 여기다. 화면만 있고 동작이 없었다.

### 둘러보기가 인물을 돌아가며 내준다

`POST /api/demo/session` (`DemoSessionController`, 프로파일 `demo & !prod`).
`DemoDataConfig.PERSONAS`를 **순서대로** 하나씩 내준다.

| | 이유 |
|---|---|
| 무작위가 아니라 순서 | 무작위면 두 창이 같은 사람이 될 수 있다 |
| 새 계정을 만들지 않는다 | 인물은 이미 방 참여자고 각자 기록이 있다. 누가 되든 채워진 화면을 본다. 방문자가 늘어도 사용자 목록이 늘지 않는다 |
| `demo` 프로파일에서만 | 비밀번호 없이 토큰을 내주므로 운영에 있으면 안 된다 |

**창을 두 개 열면 서로 다른 사람이 되고 실제로 대화가 오간다.**
그때야 `보내는 중 → 전송됨 → 전달 완료`가 상대 화면에 도착하는 것이 보인다.

> 받는 쪽 구독이 서기 전에 보내면 밀려 오지 않고 재접속 보충 조회로 채워진다.
> 실시간으로 오는 것을 보려면 상대 창이 "N명 온라인"이 된 뒤에 보내야 한다.
> e2e도 그 조건을 기다린다.

### 초대 링크

`ChatRoomService.joinRoom`이 이미 있었다(GROUP만, DIRECT는 400, 중복은 409).
화면에 없던 것은 **두 번째 사람이 들어올 길**뿐이었다.

- 그룹 대화 머리글의 `초대 링크 복사` → `…/?join=12`
- 라우터를 들이지 않는다. 화면이 하나인 앱에 그것 하나 때문에 의존성을 늘릴 이유가 없다
- 링크를 열면 로그인 여부에 따라 바로 참여하거나, 로그인 뒤 참여한다
- **409(이미 참여 중)는 성공으로 다룬다.** 방을 열어 주면 된다
- 값을 꺼내는 순간 주소창에서 지운다. 새로고침마다 다시 참여를 시도할 이유가 없다

### 데모 데이터가 소품처럼 보이지 않게

- 인물 이름을 한국 이름으로. **Alice·Bob은 교과서 placeholder라 읽는 순간 소품인 게 보였다**
- **대본에서 내 다른 프로젝트 이야기를 걷어냈다.** "대기열 화면", "좌석표 쪽", "구역 순서"가
  나오면 가짜 팀이 내 포트폴리오를 이야기하는 꼴이 된다
- 그룹 방 2개 → 4개, 여섯 명이 모두 참여. 누가 되든 목록이 비지 않는다
- 1:1은 짝마다 다르게 둔다. 누가 되느냐에 따라 목록이 달라지는 게 자연스럽다

> **e2e를 돌리면 데모 데이터가 더러워진다.** 테스트가 실제로 메시지를 보내기 때문이다.
> 캡처 전에는 `down --volumes`로 비우고 다시 올린다. 시드는 방이 하나도 없을 때만 돈다.

> 공개 배포가 아니라서(포트폴리오가 적어 둔 주소가 `localhost:14173`) 공유 방을 두었다.
> **공개로 바꾸면 이 전제가 깨진다.** 누구나 쓰는 방이 되므로 그때는 다시 생각해야 한다.

## 안내봇

혼자 창 하나만 연 사람에게도 무언가 일어나야 한다. 창 두 개를 열 수 없는 사람에게는
초대 링크도 소용이 없다.

### 봇으로 보이게 만든다

이름 옆에 **`BOT` 배지**가 붙는다. 근거는 `users.bot` 컬럼이다(`V2` 마이그레이션):
화면에서 닉네임을 문자열로 비교하는 꼼수를 쓰지 않는다. Slack·Discord도 `is_bot`을
핵심 모델에 갖고 있다.

**사람인 척하는 스크립트를 넣지 않는다.** 그건 방금 걷어낸 Alice·Bob으로 되돌아가는 것이고,
읽는 사람이 진짜 사람이라고 오해하므로 더 나쁘다.

> 컬럼은 제품의 사실이고, **`안내봇`이라는 인물과 응답 규칙은 데모다**(`demo & !prod`).

### 파이프라인을 우회하지 않는다

봇도 `ChatMessageEvent`를 만들어 `ChatMessageProducer`로 보낸다.
사람이 보낼 때와 **완전히 같은 경로**(Kafka → DB 커밋 → 브로드캐스트)다.
소켓에 바로 찔러 넣지 않는다. 그래야 봇의 말도 "저장된 뒤에만 전달된다"는 약속 안에 있다.

### 왜 별도 컨슈머 그룹인가

`chat.messages`에 **자기 그룹(`chat-bot`)으로** 붙는다(`KafkaConfig.chatBotListenerFactory`).

| | |
|---|---|
| 인스턴스가 2대인데 같은 그룹이라 **한 대만 처리** | 두 번 답하지 않는다. 여기가 제일 틀리기 쉬운 곳이라 e2e가 답이 하나인지 센다 |
| 저장 컨슈머를 건드리지 않는다 | 봇이 터져도 전달 보장이 흔들리지 않는다. 같은 리스너에 두면 봇의 예외가 Kafka 재전달을 부른다 |
| 무슨 일이 나도 `ack` 한다 | 봇이 못 답했다고 같은 메시지를 계속 다시 읽으면 결국 멈춰 선다. 봇은 있으면 좋은 것이지 보장 대상이 아니다 |

### 좁게 답한다

| | |
|---|---|
| `@안내봇` 멘션 · `/` 명령 | 답한다 |
| **그 밖의 모든 말** | 답하지 않는다 |
| 보낸 이가 봇 | 답하지 않는다 (무한 루프 차단) |

아무 말에나 답하면 방문자가 떠난 뒤에도 데모 데이터가 계속 불어난다.
규칙은 `ChatBotRules`에 순수 함수로 있다. LLM을 붙이지 않아 **답이 매번 같고 테스트로 고정된다.**

### 정기 공지

평일 09:30 스탠드업, 18:00 마감(`ChatBotScheduler`).

- 인스턴스가 2대라 **타이머도 2벌 돈다.** `pg_advisory_xact_lock`으로 한 트랜잭션만 들어오게 막는다
- 잠금을 잡은 뒤 **오늘 이미 보냈는지 다시 센다.** 잠금만으로는 재시작 때 같은 날 두 번 도는 것을 못 막는다
- 스케줄링은 `ChatBotSchedulingConfig`에서 **데모 프로파일에만** 켠다. 운영에는 정기 작업이 없다

> 짧게 둘러보는 동안 정각을 만나기는 어렵다. 그래서 **시드에 봇의 지난 공지를 넣는다.**
> 방을 열면 기록에 남아 있어 "계속 돌고 있는 서비스"로 읽힌다.

### 알아 둘 것

- 둘러보기 회전 카운터는 **프로세스마다 따로 돈다.** 인스턴스가 2대라 연달아 부르면
  같은 사람이 두 번 나올 수 있다. 창 두 개가 서로 달라야 하는 것은 e2e가 지킨다
- **볼륨을 비우면 사용자 id가 밀린다.** 봇을 먼저 시드하므로 id 1이 봇이 된다.
  브라우저에 남은 옛 토큰으로 들어가면 엉뚱한 사람이 된다. 초기화 뒤에는 저장소도 비운다

## 제품 안에 제품 설명을 넣지 않는다

지운 것: 머리글의 `How it stays correct` 서랍(DB transaction·optimistic 전송 설명),
로그인 화면의 `Realtime delivery lab`·`01 SENDING / 02 ACCEPTED / 03 PERSISTED`,
사이드바의 `저장 경계를 확인하는 채팅`, 빈 대화의 큐·DB 안내, 머리글의 사용자 id.

**고지는 남긴다.** 공개 배포라 누구나 가입할 수 있으므로 로그인 화면 양식 아래에
"테스트 환경입니다. 대화 내용은 예고 없이 초기화될 수 있습니다."를 조용히 둔다.
그건 제품 설명이 아니라 고지다.

글자 수(`0/2,000`)는 한도에 가까워질 때만 보여준다. 메신저가 늘 띄워 두는 값이 아니다.

## 왜 이 방향인가

채팅은 **오래 켜 두는 화면**이다. 몇 초 보고 닫는 화면이 아니라 하루 종일 옆에 둔다.
그래서 밝고 강한 색이 아니라 어둡고 조용해야 하고, 정보가 조밀하되 눈이 아프지 않아야 한다.
Linear가 그걸 푼 방식이 **굵기 대신 회색 계단으로 위계를 만드는 것**이다.
weight는 510에서 크게 벗어나지 않고, 대신 글자색이 네 단계로 갈린다.

그리고 채팅은 키보드로 하는 일이다. 방 전환·검색·전송이 전부 손가락이 홈 포지션에 있을 때
일어난다. 그래서 **명령 팔레트와 단축키가 장식이 아니라 기능**이다.

포트폴리오의 다른 프로젝트와 겹치지 않는다.
좌석 예약은 사진 포스터와 배너, FinMate는 밝은 민트 클레이 모바일이다.
여기는 **조밀한 다크 메신저**다.

## 토큰

```css
--bg:        #08090a;   /* 가장 아래 */
--surface:   #0e1011;   /* 목록·사이드바 */
--raised:    #16181a;   /* 입력창·떠 있는 것 */
--line:      rgba(255,255,255,0.07);   /* 선이 아니라 아주 옅은 면 */
--line-firm: rgba(255,255,255,0.13);   /* 포커스된 경계 */

--text:      #f7f8f8;   /* 본문 */
--text-2:    #d0d6e0;   /* 보조 */
--text-3:    #8a8f98;   /* 메타: 시각·상태 */
--text-4:    #80848c;   /* 가장 흐린 것. 여기서 더 흐려지면 안 읽힌다 */

--accent:    #7c8cff;   /* 하나. 내 메시지와 포커스에만 */
--ok:        #4ade80;   /* 전달 완료 */
--warn:      #fbbf24;   /* 보내는 중 */
--danger:    #f87171;   /* 실패 */
```

**위계는 굵기가 아니라 색이 만든다.** weight는 450~550 사이에 둔다.
굵기로 강조하기 시작하면 조밀한 화면이 얼룩덜룩해진다.

대비: `--text-4`(#80848c)는 `--bg` 위 **5.31:1** · `--surface` 위 5.08:1 · 네이비 패널 위 4.80:1.
**이보다 흐린 색을 만들지 않는다.**

처음엔 Linear에서 본 `#62666d`를 그대로 적어 두고 "4.6:1"이라고 썼다. **틀린 숫자였다.**
실제로는 3.45:1이다. 눈으로 충분해 보였을 뿐 계산하지 않았다.
색을 정할 때는 재고 적는다.

## 타이포

| 이름 | 크기 | 굵기 | 자간 | 쓰는 곳 |
|---|---|---|---|---|
| `.title` | 20px | 550 | -0.02em | 화면 제목 |
| `.body` | 14px | 450 | -0.01em | 메시지 본문 |
| `.meta` | 12px | 450 | 0 | 시각·상태·닉네임 |
| `.kbd` | 11px | 500 | 0 | 단축키 표시 |

본문이 14px인 이유: 채팅은 한 화면에 많이 담아야 한다. 16px이면 대화가 짧아 보인다.

- 그림자를 쓰지 않는다. 떠 있는 것은 배경색 한 단계와 옅은 테두리로 표현한다

## 교차 노드 e2e: 원인을 찾았고 통과한다

한동안 `e2e/chat-flow.spec.ts:210`("app-1 delivers to app-2 exactly once across
recovery boundaries")이 로컬에서 통과하지 않았다. **앱 결함이 아니라 실행 환경 문제였고,
그중 하나는 compose의 실제 결함이었다.**

처음에 나는 "주입된 장애에서 회복해 화면이 따라잡는 시간이 모자란 것 같다"고 적었다.
**틀린 추정이었다.** 장애 주입은 그 단언보다 뒤에서 켜지고, 단언 시간은 이미 15초였다.
로그에서 본 장애 문구가 앞선 실행에서 남은 것인데 그걸 원인으로 삼았다.

실제로 찾은 것은 셋이다.

1. **오버레이 없이 돌리고 있었다.** 데모 게이트웨이는 `/ws/app-1`을 일부러 404로 막는다
   (노드 정체를 숨기는 게 공개 데모의 요건이고, 그걸 검증하는 테스트가 따로 있다).
   노드를 지정해 붙는 e2e는 `docker-compose.e2e.yml`을 겹쳐야 열린다. CI는 그렇게 한다.

2. **nginx가 업스트림 IP를 시작 시 한 번만 해석한다.** 앱 컨테이너만 다시 만들고
   게이트웨이를 두면, `/ws/app-1`이 조용히 app-2로 간다. 실제로 Alice가 app-1에 붙었는데
   `x-app-instance`가 app-2로 왔다. 게이트웨이를 함께 재시작해야 한다.

3. **Kafka 로그와 Postgres의 수명이 달랐다.** Postgres는 명명 볼륨이라 살아남는데
   Kafka에는 볼륨이 없어 컨테이너를 다시 만들 때마다 오프셋이 0부터 시작했다.
   그러면 새 메시지의 `(partition, offset)`이 예전 행과 겹치고
   `uk_messages_kafka`에 걸려 저장이 영영 재시도에 빠진다. 저장되지 않으니 전달도 없다.
   멱등성 장치는 제 일을 하고 있었다. 두 저장소의 수명이 어긋난 게 문제였다.
   `docker-compose.demo.yml`에 Kafka 볼륨을 추가해 맞췄다.

깨끗한 스택에서 5회 연속, 전체 스위트 2회 연속 통과한다.

### 여기서 배운 것

로그에 보이는 오류가 지금 이 실패의 원인이라는 보장이 없다. 스택이 오래 떠 있으면
로그에는 여러 실행의 흔적이 섞인다. 시간을 맞춰 보지 않고 눈에 띄는 문구를 집었더니
엉뚱한 원인을 문서에까지 적었다.

그리고 "원본에서도 실패하니 내 변경 탓이 아니다"는 확인은 절반만 맞았다.
양쪽 다 **같은 잘못된 방법으로** 돌렸기 때문에 둘 다 실패한 것이었다.
비교는 방법이 옳을 때만 뜻이 있다.

## 이 재작성이 실제로 깨뜨린 것: 대비 회귀

`.conversation-header`에 예전 밝은 테마의 `rgba(255,255,255,0.92)`가 남아 있었다.
어두운 배경 위에 흰색 92%를 얹으면 `#ebebeb`이 되고, 그 위에 내가 새로 넣은 밝은 글자
`#f7f8f8`이 놓여 **1.12:1**이 됐다.

내 대비 점검이 이걸 놓친 이유: **스타일시트를 읽어서 확인했기 때문이다.**
색은 겹쳐서 만들어지는데 파일에는 겹치기 전 값만 있다. 브라우저에 계산된 값을 물어보니
한 번에 나왔다. 앞서 `rgba(245,247,251,0.96)`을 놓친 것도 같은 이유였고,
같은 실수를 두 번 했다.

남아 있던 밝은 값 세 개를 전부 토큰으로 바꿔 앱 전체가 한 계단 위에 서게 했다.

## 데모 데이터 (2026-08-07)

전에는 사용자 둘만 만들고 대화는 없었다. 데모를 열면 빈 화면이었고, 시연하려면
그 자리에서 대화를 만들어 세 마디를 주고받아야 했다. 그렇게 찍은 화면은
**메신저가 아니라 기능 테스트로 보인다.**

쓰던 메신저처럼 보이려면 대화가 여럿이고 각각 과거가 있어야 한다.

| | 지금 |
|---|---|
| 사용자 | 6명 (Alice · Bob · 유진 · 도현 · 세미 · 하람) |
| 대화 | 5개: 1:1 셋, 그룹 둘 |
| 메시지 | 22건, 닷새에 걸쳐 |
| 시각 | 업무 시간대(09:20~)로 고정 |

시각을 `now()` 기준으로 두면 컨테이너를 새벽에 띄웠을 때 모든 대화가
"오전 3시"에 오간 것이 된다. 실제로 그렇게 나왔다.

대화 목록의 시각도 고쳤다. 시각만 찍으면 어제 온 메시지와 오늘 온 메시지가
똑같이 "오전 09:14"로 보인다. 오늘은 시각, 어제는 "어제", 그 이전은 날짜로 적는다.

### 시드가 드러낸 것

메시지만 과거로 옮기고 방·참여 시각을 현재로 뒀더니 읽음 처리가 400이 났다.
"참여 이전 메시지는 읽음 기준으로 사용할 수 없습니다". **앱의 규칙이 맞다.**
들어오기 전 메시지를 읽었다고 표시할 수는 없다. 시드가 만든 시간이 앞뒤가 안 맞았던 것이다.
방과 참여 시각도 함께 과거로 옮겨 고쳤다.

데모가 비어 있을 때는 이 경로가 아예 돌지 않아 드러나지 않았다.
데이터를 진짜처럼 만들면 진짜 경로가 돈다.
